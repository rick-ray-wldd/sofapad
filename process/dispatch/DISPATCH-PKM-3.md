## 2. 成功條件
1. **先研究可行方案，寫進 DECISIONS 並附來源。**
   - **方案 A：Web Speech API。**
     - 查 iOS Safari 和「加入主畫面」的 Web App 支不支援 `webkitSpeechRecognition`。
     - 能不能切 zh-TW 和 en-US。
     - 需不需要安全來源（HTTPS）。
     - 辨識是不是走 Apple 伺服器。
   - **方案 B：手機錄音，Mac 辨識。**
     - 手機用 `getUserMedia`／`MediaRecorder` 錄音，送到 Mac，由 Mac 本機辨識（例如 macOS 的 Speech framework）後輸入。
     - 這條路是不是也需要 HTTPS。
   - **現況的限制：**
     - 現在網頁是 `http://<Mac>.local:8765`，不是安全來源。
     - 如果一定要 HTTPS，提出免費、不改系統設定的作法，例如 Mac 端自簽憑證，加上 Ray 在 iPhone 安裝並信任描述檔。
     - 寫成「Ray 要做的步驟」，不要自己繞過任何安全機制。
   - **查證：**純網頁能不能用程式叫出 iOS 鍵盤的聽寫。總控認為不行。
2. **照研究結果，實作最可行的方案。**
   - **按鍵位置：**直拿和橫拿全螢幕都有一個明顯的 🎤 鍵；橫拿時放在左側浮動工具列。
   - **操作方式：**
     - 按一下開始，或按住說話，二選一，並寫明理由。
     - 錄音中要有清楚的狀態，也要能取消。
   - **語言：**中文和英文可以切換，或自動判斷。
   - **送出前確認：**
     - 辨識結果先顯示在小預覽框，Ray 按「送出」才傳到 Mac，避免誤送。
     - 設定裡可以改成「辨識完直接送」。
     - 預覽框裡能刪改文字。
   - **傳到 Mac：**走現有的文字輸入通道。配對、HMAC、區網限制都不能拿掉。
   - **做不到時：**麥克風權限被拒、不支援、或不是 HTTPS 時，手機上要清楚顯示原因和替代做法，例如「先用 Aa 鍵盤的麥克風」或「照 README 安裝憑證」。
3. **測試**

   - 瀏覽器層級測試：headless Chrome 可以用假的 SpeechRecognition 或錄音 API。

   - self-test 全過。
   - 真 iPhone 的語音只能 Ray 測，列入「還沒驗證」。
   - 真實注入的限制同 PKM-2 §2-5。
4. **紀錄：**照 PROTOCOL.md v1.1 寫：

## 6. 補充 PKM-3-1（2026-10-27 00:22，Ray 的 P-20：聽寫疊字和按鍵列自訂）

**優先順序改成這樣：先做 ① 疊字，再做 PKM-3 的語音鍵，最後做 ② 按鍵列。** ① 影響 Ray 現在每一次輸入。

### ① 聽寫送到 Mac 會疊字（P0）
- **症狀：**
  - Ray 用 iPhone 鍵盤的聽寫說話，手機輸入框裡的文字是對的，但 Mac mini 收到的字和詞會重複。
  - 例如「打字，打字，打字」「然後然後」「鍵盤鍵盤鍵盤」。
  - P-19 和 P-20 是總控實際收到的樣本，請拿來對照。
- **先重現再修，根因寫進 ISSUES。**總控看程式碼猜到的方向，供參考，不代表結論：
  - (a) `app.js` 在「即時」模式，輸入框超過 200 字約 1.5 秒後會自動清空並 `mirror.reset()`。iOS 聽寫可能還保留它自己的辨識結果，之後又整段改寫回來，於是整段重送。
  - (b) iOS 聽寫邊聽邊改字。改的是前面的字時，會變成「刪 N 個字＋插入」；如果 Mac 端的退格沒有全部生效（例如退格被截斷、送太快掉事件），舊字就會留下來。
  - (c) 聽寫可能先插入一個佔位字元（例如 U+FFFC），或者不觸發 composition 事件，導致差異比對的基準錯了。
- **做法建議：**
  - 加一個只存在本機的除錯紀錄：記下 inputType、composition 事件、value 長度和每次送出的 ops，不上傳。用它錄一段 iOS 聽寫的事件序列。
  - 寫成單元測試重播。
  - 修法可以考慮：聽寫進行中先緩衝，停頓後一次送出差異；避免在輸入中自動清空；Mac 端核對退格確實執行。
  - 要附前後對照的測試。
- **真 iPhone 的確認要 Ray 做**，列入「還沒驗證」。可以在 README 寫一個簡單的測試句，讓 Ray 照著念。

- **進入方式：**由你設計，例如在按鍵列長按，或在列尾放「編輯」鍵。寫進 DECISIONS。
- **版型：**直拿和橫拿都要能用。橫拿時要確認不會擋住觸控板。

## 8. 補充 PKM-3-3（2026-10-27 00:52，Ray 的 P-22：送出後舊文字又被送到下一個 App）
- **症狀：**
  - Ray 用聽寫說完、按送出後，手機輸入框裡的文字沒有真正清掉。
  - 他接著切到 Mac 的下一個地方，例如從 Orca 換到 LINE，剛才那整段又被送進 LINE。
  - 這會把私人內容送到別人那裡，屬於 **P0**，和 ① 疊字一起處理、一起交付。
- **總控的猜測（供參考，請以重現結果為準）：**
  - `sendBuffered()` 雖然把 `input.value` 清成空字串，但 iOS 聽寫或輸入法還保留著自己的內容。輸入框沒有 blur，聽寫也沒有結束，下一次有 input 事件時就把整段插回來。
  - 「即時」模式重新同步，或切換模式時的 `live.flush()`，也可能把殘留文字當成新文字送出。
- **要求：**
  - 送出（含 Enter 自動送出）以後，手機上的內容必須真正清空，而且不會因為之後的任何操作再送一次。可以考慮：送出前先 blur 結束聽寫或輸入法、清空後檢查、對同一段文字做防重送。
  - 加一個重播測試：「聽寫 → 送出 → 再輸入或切模式」，確認不會重送。
  - README 加一段給 Ray 的真機測試步驟：在 Orca 說一句 → 送出 → 切到 LINE 打一個字，確認不會帶出前一句。
- 其他規定和 PKM-3 §3–5 相同。
